# VC — Summary

## What this domain does
Implements the full Verifiable Credentials stack: credential issuance, presentation, and verification at the core level; the OID4VCI and OID4VP protocol layers for standards-compliant flows; credential format serialization (SD-JWT, W3C JSON-LD); and supporting subsystems for metadata, status, proof-of-possession, DCQL, and presentation exchange. This is the largest domain in the SDK.

## Key decisions / constraints
- OID4VCI uses a dual-error split: `ProtocolError` (4xx — returned to the client) vs `InternalError` (5xx — server-side fault).
- OID4VP JWE encryption for `direct_post.jwt` response mode is handled via `one-core-portable`; the optional `JweDecrypt` KMS capability must be present on the verifier's KMS.
- `mso_mdoc` format support is gated and excluded on wasm targets.
- `Credential` and `Claims` implement `ZeroizeOnDrop` to scrub sensitive data from memory.
- DCQL and Presentation Exchange are both supported query formats; the verifier decides which to use per request.
- **OID4VP client-id prefixes (request generation):** fragment response modes use a `redirect_uri` client; for the signed-request modes the prefix of the verifier's configured `client_id` selects the signer — `x509_san_dns:<SAN-DNS>` and `x509_hash:<leaf-hash>` sign with the cert chain in the JWT `x5c` header (chain supplied by `VerifierBuilder::with_x509_certificate_chain`, PEM, leaf first), any other prefix signs as a `decentralized_identifier` client. Before signing, the verifier enforces that the leaf both derives the configured `client_id` and certifies the KMS signing key — the Wallet checks the request signature against that leaf, so an incoherent pair would otherwise only fail on the Wallet side. Generation-only, and the signing path is native-only (the upstream `X509Client` needs a `Send + Sync` signer → `KH: 'static`); the holder does not yet consume X.509 requests. The **chain API itself is not target-gated**: `VerifierMetadata.x5c_chain` and `with_x509_certificate_chain` carry PEM bytes rather than parsed `Certificate`s, so the Verifier has one shape everywhere and only `build_x509_request` is `#[cfg(not(wasm32))]` — `x509-cert` is a non-wasm dep, and storing parsed certs would make the field and its setter disappear on wasm. The builder still parse-and-discards on native so a malformed chain fails at build time. In practice only Node.js sees any of this: neither the wasm nor the uniffi wrapper exposes an OID4VP Verifier. `default_wallet_metadata()` advertises both x509 prefixes, which is what makes them usable in cross-device flows (no Wallet Metadata is exchanged there, and the upstream builder rejects unadvertised prefixes). The certificate logic lives in its own `oid4vp/x509.rs` (aliases, `client_id_from_x509_chain`, `ensure_leaf_matches_signing_key`), which carries exactly two `#[cfg]`s — the `X509Client` / `X509Variant` aliases for all targets, then a `#[cfg(not(wasm32))] mod native` re-exported wholesale — rather than one per item; `verifier.rs` re-exports the type aliases so `verifier::*` paths resolve, and `oid4vp/mod.rs` re-exports only `X509Variant` for wasm (nothing there can construct an `X509Client`). `client_id_from_x509_chain(chain, variant)` derives the `client_id` a chain implies (SAN DNS name or leaf hash) by wrapping upstream `X509Client::client_id`, which `X509Client::new` also calls, so a caller can never configure one the request path would then reject; it is the only practical way to get an `x509_hash` `client_id`. That upstream entry point (oid4vp-rs, ASI-6960) derives an id without a placeholder `Signer`, and errors on an empty chain rather than indexing `x5c[0]` — which matters because the call is reached across an FFI boundary, where a panic aborts the host process. Exposed to Node.js as `OID4VPVerifierBuilder.withX509CertificateChain` plus `ClientId.fromX509SanDns(dnsName)` / `ClientId.fromX509CertificateChain(pem, X509Variant)`, with `ClientId` readable back through the `fullId` / `prefix` / `id` getters (no `toString`/`toJSON` — callers name `fullId` explicitly) so a caller can persist and compare the derived identifier, which matters because rotating a leaf certificate changes an `x509_hash` `client_id` (not exposed in WASM/UniFFI).
- **`default_client_metadata()` now advertises `mso_mdoc`** alongside `dc+sd-jwt` — the EUDI wallet presents its PID as mso_mdoc, and a verifier that does not advertise the format is never matched. `issuerauth_alg_values` and `deviceauth_alg_values` are both `[-7, -8]` — COSE `ES256` and `EdDSA`. That is deliberately narrower than the `[-7, -8, -9, -19]` one-core advertises: one-core's `extract_algorithm_from_header` maps only `ES256`/`EdDSA` and hard-fails on anything else, so `-9` (`ESP256`) and `-19` (`Ed25519`) would claim support neither it nor we have. Advertise only what verification accepts — the wallet-side check is an intersection test (`is_supported`), so `[-7, -8]` still matches one-core wallets. `default_wallet_metadata()` deliberately does **not** list `mso_mdoc` (it carries `dc+sd-jwt` and `ldp_vc`). Verification of such a VP still requires issuer trust anchors via `VerifierBuilder::add_trusted_root_certificate`.
- **Consumer-supplied `client_metadata` is checked against what verification accepts**, both on `VerifierBuilder::build` and per request (`AuthorizationRequestMetadata.client_metadata`), by `unsupported_vp_formats`. The ceiling is `VERIFIABLE_VP_FORMATS` — every format `verify_presentation` has an arm for — and **not** the default advertisement: `ldp_vc` is verified but not advertised by default, so checking against `default_client_metadata()` rejected every JSON-LD verifier (all four OID4VP e2e flows). `ldp_vc` is claimed with an empty payload, i.e. no `proof_type` ceiling, because the suite comes from the credential's own proof via `ssi`'s `AnySuite`; `dc+sd-jwt` and `mso_mdoc` do pin their algorithm lists, which is where the check earns its keep.
- **Delegate SD-JWT — §7.1 "delegation using presentation", gated `delegate-sd-jwt` (off by default, EXPERIMENTAL — tracks an unstable IETF draft).** A `delegate` `transaction_data` item turns an OID4VP presentation into a delegation grant, handled **transparently in the normal present/verify flow** — no bespoke methods, no client-side branching.
    - **Holder (grant):** `present_credentials(_auto)` produce a **dSD-JWT** for any credential whose presentation input is targeted by a `delegate` item — the decision lives per-credential in `create_presentation_by_input` (no `grant_delegation` method), via core `create_delegated_presentation` → `formats::dsd_jwt::SdJwtAPI::create_delegated_credential` (thin wrappers over `sd_jwt_rs`). Because the choice is per-credential, mixed `transaction_data` (delegate + ordinary) and multi-credential delegation are supported.
    - **Holder binding:** the grant **is** a Holder-bound presentation — the Holder signs the KB-SD-JWT (proof of possession, verified by the chain walk against the issuer/preceding `cnf`). The request `aud`/`nonce` (from the `HolderBinder`) are written into the delegate payload; for a plain dSD-JWT (no trailing KB-JWT) the final KB-SD-JWT link is the key binding, and `sd_jwt_rs` verifies `aud`/`nonce` from that link's Delegate Payload. The wire constants live in `oid4vp/delegate.rs`.
    - **Verifier (accept/verify):** `oid4vp::Verifier::verify_and_extract_presentation` runs the normal verification and also returns the raw presentations per credential id, so a Delegate Holder can **store** the grant; `verify_presentation` returns just the claims. A delegate-targeted credential is verified as a *grant*, not a presentation — its newest hop may still hold every requested alternative un-narrowed (AP2's stored grant carries a checkout-open and a payment-open mandate side by side), which `SDJWTVerifier::verify_presentation` rejects — so `do_verify_presentation` routes it to `vc::core::Verifier::verify_delegation` → `DsdJwtPurpose::Delegation`: same checks minus narrowing, with the request `aud`/`nonce` required in **every** disclosed alternative of the final hop, since an unbound sibling could be narrowed to later and replayed against any Verifier. The result comes back in two halves — `issued_vc` and `delegations` — and `validate_delegate_transaction_data_content` requires that hop's alternatives to be **exactly** the `delegate` items that targeted the credential.
    - **Wallet-side discovery:** under `delegate-sd-jwt`, `Credential::parse_claims` (SD-JWT) uses `sd_jwt_rs::utils::decode_dsd_jwt` to layer each chain link's `delegate_payload` onto the issuer claims, so a stored grant's delegate-injected claims (e.g. `purchase_id`) are visible to DCQL value-matching. This lets a Delegate Holder store the grant in its vault and re-present it with `present_credentials_auto` (rather than an explicit `CredentialMapping`). Unverified — selection only; the Verifier re-verifies the chain.
    - **Still open:** a stored menu grant is never narrowed when *presenting* it downstream — `SDJWTHolder::select_delegate_alternative` is never called and `DelegationParams::drop_disclosures` is always `None` — so it can be received, stored and re-delegated, but not presented.
    - **Crate feature dependency:** the feature forwards to `sd-jwt-rs/delegate` (`delegate-sd-jwt = ["sd-jwt-rs/delegate"]`). `sd_jwt_rs` gates all chain support — holder delegation, `decode_dsd_jwt`, and **chain-aware verification** — behind its `delegate` feature, so every role that touches the chain (Holder, Agent, **and the verifying Merchant**) must enable `delegate-sd-jwt`.
    - With the feature **off**, a `delegate` item is rejected as an unrecognized type (OID4VP §5.1 conformance), not hashed-and-ignored.
