# Release notes draft — 1.1.0

Draft of the `NOTES.md` for the `1.1.0` tag ([release guide](../guidelines/release.md#3-write-the-release-notes)).

---

- [feat] Export the anchors of an ETSI trust list — a TS 119 612 List of Trusted Lists with its member Trusted Lists and the TS 119 602 LoTEs it points to, or a TS 119 602 LoTE (JWT, bare or wrapped in a `LoTE` member as the published EU lists are, or XML) — authenticated against pinned signers, with each anchor's role, service type, service status, source list and its `NextUpdate`; members that fail are reported with a reason, and LoTE services left out for their status are listed (`excludedServices`) (`vc::trust::list::export_trust_list`, Node `exportTrustList(url, kind, options?, httpClient?)`). Lists are fetched over `https` only, without redirects, holding at most `maxDocumentBytes` of each. Each document is bounded by `documentTimeoutSeconds` (default 30) and the whole export by one deadline and one pointer budget: a member over its timeout is skipped as `unreachable`, members left at the deadline as `deadline`, and only the root failing fails the export. A failure has a stable code (`trust_list_<reason>`, Node `TrustListError`)
- [feat] Evaluate the issuer of every presented SD-JWT VC and mdoc against trust anchors that need not be CAs (`VerifierBuilder::add_trust_anchor`, Node `OID4VPVerifierBuilder.addTrustAnchor({ pem, sourceRef, role, serviceType })`), and return it per credential with the matched anchor's `sourceRef` and `role`. Only an anchor without a `serviceType`, or of an issuing trust-list service (TS 119 602 `…/Issuance`, or an issuing TS 119 612 type), anchors issuers; others, e.g. a revocation service's, only check status-list signatures (`verify_and_extract_presentation_with_issuer_trust` → `issuer_trust`, Node `verifyAndExtractPresentation` → `issuerTrust`)
- [feat] Issuer trust mode `enforce` (default) or `report` (`VerifierBuilder::with_issuer_trust_mode`, Node `withIssuerTrustMode`). `report` returns untrusted issuers in the result instead of failing; every other check — signatures, chain integrity, validity and key usage, revocation of a chain that reaches an anchor, holder binding, nonce, audience, status and transaction data — still fails the verification. The status list of a trusted issuer must still validate up to an anchor, as under `enforce`; that of an untrusted issuer is checked for integrity, and for revocation where its chain reaches an anchor
- [feat] **Breaking:** issuer trust per credential category (EUDI ARF OIA_12 to OIA_15). Each presented credential is classified as a PID, QEAA, PuB-EAA or EAA from its `vct` / mdoc docType and its `category` claim (`urn:etsi:esi:eaa:eu:qualified` is a QEAA, `urn:etsi:esi:eaa:eu:pub` a PuB-EAA; a type listed in the classification wins over the claim, and a verifier relying on the claim must request it), and its issuer is trusted only under anchors whose `role` fits: `pid_provider`, `qeaa_provider`, `pub_eaa_provider` or `eaa_provider`. The EUDI PID types (`urn:eudi:pid:*`, `urn:eu.europa.ec.eudi:pid:*`, `eu.europa.ec.eudi.pid.1`) are always PIDs; `VerifierBuilder::with_credential_classification` (Node `withCredentialClassification({ pid, qeaa, pubEaa })`) adds types to each category. Anchors without a role, such as trusted root certificates, fit every category unless `with_roleless_anchors(RolelessAnchors::EaaOnly)` (Node `withRolelessAnchors('eaa_only')`). With issuer anchors supplied but none for the category, the issuer is `untrusted` with the new reason `no_anchors_for_category`. Every evaluated issuer trust entry, and the `IssuerNotTrusted` details, carry the new `category` (delegation grants carry none). What changes for callers: an anchor whose role is none of the four (e.g. `wallet_provider` or a custom string) no longer anchors any issuer; an anchor labelled `pid_provider` no longer anchors an mDL, which is an EAA, so label it `eaa_provider` or classify the mDL docType as a PID; `IssuerTrustOutcome` and `IssuerTrustConfig` gain fields (Rust)
- [fix] Only trust-list services that issue attestations anchor issuers: TS 119 602 `…/Issuance` services and the TS 119 612 types `EAA`, `EAA/Q`, `EAA/Pub-EAA` (and the EUDI pilot PID type). Qualified CAs for e-signatures and e-seals (`CA/QC`, `CA/PKC`) no longer do, so a qualified e-seal can no longer sign a credential that verifies as trusted. A trust-list export no longer emits services without an issuer role (qualified CAs, time stamping, OCSP, CRL), which also keeps a full EU LoTL export small. Requires `equs-one-core` with the export change
- [feat] `TrustListExport.next_update` (Node `nextUpdate`, RFC 3339): the root list's `NextUpdate`. A member list's anchors carry only their own `source_next_update`, so a consumer that checked only that kept national-list anchors alive after the EU LoTL that vouched for them had expired; treat an anchor as stale at the earlier of the two
- [feat] Node `EqusSdkError` gains an optional `details`. For `IssuerNotTrusted` it holds every presented credential's issuer trust, in the same camelCase shape as `issuerTrust` (`credentialId`, `index`, `status`, `anchorSki`, `sourceRef`, `role`, `reason`, `category`)
- [fix] **Breaking:** an untrusted credential issuer fails with the new `IssuerNotTrusted` error (message `issuer_not_trusted: <JSON>`, Node code `VpInternalError.IssuerNotTrusted`) instead of a certificate error such as `Issuer certificate chain is not trusted`. This applies to every OID4VP verification — Node `verifyPresentation` as well as `verifyAndExtractPresentation`
- [feat] DCQL `trusted_authorities` (OpenID4VP 1.0 §6.1.1, required by HAIP 1.0 §5): a credential query can carry `aki`, `etsi_tl`, `openid_federation` and other entries, kept through the signed request and the session (Node `DcqlCredential.trusted_authorities`). `vc::trust::trusted_authorities::derive_trusted_authority_akis` (Node `deriveTrustedAuthorityAkis(anchors)`) gives the `aki` values for a verifier's issuer anchors: a CA's Subject Key Identifier, a listed signing certificate's Authority Key Identifier. A presented credential must carry one of its query's `aki` values in its issuer chain, or the verification fails with `TrustedAuthorityMismatch` (Node `VpInternalError.TrustedAuthorityMismatch`) in either issuer-trust mode; `etsi_tl` and `openid_federation` are passed through, not evaluated. The check runs before the `Enforce` decision, so an untrusted issuer that also misses gives `TrustedAuthorityMismatch`. On wasm, where no issuer chain is evaluated, a query with only `aki` entries always fails. A padded `aki` value is accepted. The holder parses the same model, so it now refuses an authorization request whose `trusted_authorities` is malformed (an empty list, an entry without values, or an `aki` value that is not base64url), where it used to ignore the member. Requires `equs-openid4vp` with `trusted_authorities`
- [fix] **Breaking (Rust):** the `vc::core::Verifier` trait gains `verify_presentation_with_issuer_trust`, returning `IssuerTrustVerification { claims, outcome, issuer_chain_akis }`, which the OID4VP verifier now calls. Its default implementation evaluates nothing: it reports `not_evaluated` / `no_anchors_configured` with no issuer chain, so a custom `Verifier` type that does not override it fails every presentation under `enforce` and every `aki`-only `trusted_authorities` query in either mode. The SDK's `VerifierService` overrides it
- [fix] **Breaking:** under `enforce`, a certificate-identified issuer whose verifier has no trust anchors fails with `IssuerNotTrusted` (`not_evaluated`, `no_anchors_configured`). For mdoc the issuer chain was previously not checked against any anchor; for an SD-JWT VC with `x5c` the failure was a certificate error
- [fix] Certificate revocation is checked only where the CRL can be authenticated: for each certificate below the trust anchor, against its issuer. A chain that reaches no anchor is no longer revocation-checked, so a credential whose certificate names a CRL distribution point no longer fails with `CRL signer certificate is not present in the chain` (issuer-trust `report` mode, and mdoc without anchors), and its distribution points are not fetched. The anchor itself is trusted for being listed. The same applies to the signers of exported trust lists, whose revocation is checked below the pinned anchor
- [fix] CRLs are fetched without following redirects, at most 32 MiB and 30 s each, and cached in one validator shared by every verification and trust-list export, instead of being fetched again by a fresh validator on every check. A cached CRL is fetched again after 15 minutes and used for at most an hour, never past its `nextUpdate`
- [fix] Transport failures reached through one-core (did:webvh resolution, trust list export) keep their cause instead of reporting `HTTP status code is error: 0`
- [feat] **Breaking:** a PID, QEAA or PuB-EAA whose issuer is identified by a DID or a bare key rather than an X.509 chain is `untrusted` with the new reason `did_issuer_not_allowed`, and fails under `enforce` (EUDI ARF: these providers are identified by X.509 certificates; HAIP 1.0 requires X.509 issuer keys). This includes an SD-JWT VC whose `iss` is a DID but which also carries `x5c`: its signature is checked against the DID key, so the chain proves nothing about the signer. On wasm32, which resolves issuer keys from DIDs only, every such credential is refused
- [chore] Known limitation: an EAA issuer identified by a DID, a delegation grant, and every EAA issuer on wasm32 is reported as `not_evaluated` with reason `did_issuer` and is never rejected; a delegation grant's issued credential is not classified
- [chore] Require `equs-one-core` and `equs-one-core-portable` 0.2.0, which add TS 119 612 and TS 119 602 trust list support and verify RSA (PKCS#1 v1.5, PSS) and ECDSA P-384 list signatures
