# oid4vp — Context

## Purpose
Implements the OpenID for Verifiable Presentations (OID4VP) protocol layer, providing `Holder` and `Verifier` trait definitions along with their concrete service implementations. The module covers authorization request resolution, credential discovery and presentation (auto and manual), authorization response construction and submission (plain, JWE-encrypted, and Digital Credentials API modes), transaction data handling, and full VP verification including nonce and signature checks.

## Files

| File | Role |
|------|------|
| `mod.rs` | Module root: declares sub-modules, re-exports `HolderBuilder`, `VerifierBuilder`, `ProtocolError`, `InternalError`, `ErrorType`, `BuilderError`, and all `api::*` types. |
| `api.rs` | Public trait definitions (`Holder`, `Verifier`) and all shared data types: `ResolvedAuthRequest`, `PresentationSession`, `PresentationResult`, `AuthorizationResponseObject`, `AuthorizationResponse`, `AuthorizationResponseMetadata`, `AuthorizationRequestMetadata`, `AuthResponseOptions`, `CredentialVerificationMetadata`, `CredentialsMapping`, `CredentialMapping`, `FindVCsFailReason`, `IdTokenMetadata`, and protocol-level type aliases wrapping `openid4vp` crate types. Also exposes the ungated `as_delegate` accessor for transaction-data introspection. Also exposes (gated on `delegate-sd-jwt`) the `DelegationRequest` struct and the `delegate_transaction_data_item` builder. |
| `delegate.rs` | Wire constants (`TRANSACTION_TYPE_DELEGATE`, `FORMAT_DSD_JWT`, `FORMAT_DSD_JWT_KB`, `CLAIM_DELEGATE_PAYLOAD`) + re-exports of upstream `openid4vp` delegate types. Compiled only with the `delegate-sd-jwt` feature. |
| `verifier.rs` | `VerifierService<KH, KMS, NG, HC>` — concrete `Verifier` implementation: builds signed authorization request objects (by value or by reference), generates nonces, verifies VP tokens across SD-JWT and JSON-LD formats, validates transaction data hashes, handles JWE-encrypted responses and DC API response modes. Fragment response modes use a `redirect_uri` client; for every other mode the request object is signed and the configured `client_id`'s prefix picks the signer — `x509_san_dns` / `x509_hash` → `X509Client` via `build_x509_request(variant)` (cert chain in the request JWT `x5c` header), anything else → `DecentralizedIdentifierClient`. `with_x509_certificate_chain(pem_bytes)` supplies the chain; before signing, `build_x509_request` parses the PEM and enforces both that the leaf derives the configured `client_id` (SAN DNS name or leaf hash, per variant) and — via `x509::ensure_leaf_matches_signing_key` — that the leaf certifies the KMS signing key, since the Wallet verifies the request signature against that leaf; either mismatch is an `X509` error. `VerifierMetadata.x5c_chain` is `Option<Vec<u8>>` (PEM), not parsed `Certificate`s, so the struct and the setter have the **same shape on every target** — `x509-cert` is a non-wasm dep, and holding parsed certs would have forced the field and its setter to vanish on wasm. Only `build_x509_request` itself is `#[cfg(not(wasm32))]`; the wasm stub returns an `X509` error naming the refused prefix. The certificate logic itself lives in `x509.rs`; this file re-exports `X509Client` / `X509Variant` / `Certificate` so the established `verifier::*` paths keep working. |
| `x509.rs` | X.509 `client_id` support. Two `#[cfg]`s only, not one per item: the `X509Client` / `X509Variant` aliases sit at the top for all targets (the verifier's wasm stub takes an `X509Variant` to name the prefix it refuses), and everything needing `x509-cert` lives in a `#[cfg(not(wasm32))] mod native` re-exported with `pub use native::*` — `Certificate` (`x509_cert`), `client_id_from_x509_chain(chain, variant)` and `ensure_leaf_matches_signing_key(leaf, key)`. The former is a thin error-mapping wrapper over upstream `X509Client::client_id(&[Certificate], variant)` — the supported way to obtain an `x509_hash` `client_id`, which cannot be written by hand. It takes `&[Certificate]`, not an owned `Vec`, so callers holding a chain need no clone. `X509Client::new` derives its id through that same function, so a configured `client_id` and the one the request path emits cannot drift. The latter compares the leaf SPKI to the KMS key as curve points, not bytes (certificates carry uncompressed SEC1, `Key::pub_key` yields compressed). |
| `holder.rs` | `HolderService<HL, HC>` — concrete `Holder` implementation: fetches and validates authorization requests, discovers credentials via Presentation Exchange or DCQL, builds and submits authorization responses (including SIOP ID tokens), and reports credential status. Does **not** consume `x509_san_dns` requests (out of scope; still rejected). |
| `builder.rs` | `VerifierBuilder` and `HolderBuilder` — fluent builders; `VerifierBuilder` accepts KMS, nonce generator, key metadata, and optional DID resolver / client metadata, trusted root certs (`add_trusted_root_certificate`, non-wasm), and the request-signing certificate chain for an X.509 `client_id` (`with_x509_certificate_chain`, PEM, leaf first — compiled on **all** targets, storing raw bytes; it parse-and-discards on native so a malformed chain fails at build time rather than at request time, and simply carries the bytes on wasm, which has no parser and refuses `x509_*` requests anyway); `HolderBuilder` accepts KMS, vault, optional JWE decryptor, and DID resolver. |
| `jwe.rs` | `JweDecrypt` trait and `JweEncryptor` — JWE encryption of authorization responses using ECDH-ES and RSA key-wrap algorithms; `Algorithm` enum and `JwkConfig` for key negotiation. `select_enc` picks the content encryption algorithm from what the Verifier's `client_metadata` advertises and falls back to the spec default `A128GCM` — both when nothing is advertised and when nothing advertised is producible. That default used to be `A128CBC-HS256` because `one-crypto` could not do `A128GCM`; it can (`one-crypto/src/jwe.rs` handles it in `encrypt_in_place`, key derivation and the size table), so the spec default applies and the old `//TODO` is gone. |
| `jwe_utils.rs` | Internal helpers for JWE: extracting private key handles from KMS and populating JWK sets with both public and private key material. |
| `signer.rs` | `Signer<S>` — bridges `crate::crypto::SigningKey` to the `openid4vp::signer::Signer` trait so the verifier can sign authorization request JWTs. |
| `metadata.rs` | `default_client_metadata()` and `default_wallet_metadata()` — hard-coded default `ClientMetadata` and `WalletMetadata`. Both advertise `dc+sd-jwt` (EdDSA / ES256); the client default adds `mso_mdoc` with `issuerauth_alg_values` / `deviceauth_alg_values` of `[-8, -7]` — COSE `EdDSA` and `ES256`, which is exactly what verification handles and no more; the order matches the `["EdDSA", "ES256"]` the `dc+sd-jwt` entry above it lists, and carries no other meaning. Do **not** widen this to one-core's advertised `[-7, -8, -9, -19]`: its `extract_algorithm_from_header` (both `presentation_formatter/mso_mdoc` and `credential_formatter/mdoc_formatter`) maps only `ES256`/`EdDSA` and returns `None` for anything else, which is a hard `CouldNotVerify` / `MissingJOSEAlgorithm`. `-9` (`ESP256`) and `-19` (`Ed25519`) would advertise support we do not have and invite a presentation we then reject; one-core's own verifier metadata overstates its support this way. The wallet default instead adds `ldp_vc`, and advertises the `decentralized_identifier`, `redirect_uri`, `x509_san_dns` and `x509_hash` client-id prefixes. Also holds `unsupported_vp_formats(client_metadata)` and the `ensure_supported_vp_formats` guard over it, which reject consumer-supplied `client_metadata` advertising something the SDK cannot honor. **Both call sites go through the guard** — `VerifierBuilder::build` wraps its `Err` in `BuilderError::Build`, `create_authorization_request` in `InternalError::FormatNotSupported` — so the comparison itself lives in one place. Offending formats are named by their wire designation (`ClaimFormatDesignation` implements `Display`; `Debug` would print the upstream Rust variant, e.g. `Other("dc+sd-jwt")`, which is not what a consumer reading the error advertised). Metadata carrying no `vp_formats_supported` passes; metadata whose `vp_formats_supported` fails to deserialize is **reported, not waved through** — `get::<VpFormatsSupported>()` returns `Option<Result<_>>` and treating `Some(Err(_))` as "nothing unsupported" would fail open. It compares against `VERIFIABLE_VP_FORMATS`, **not** `DEFAULT_CLIENT_METADATA`: the capability ceiling is every format `vc::core::VerifierService::verify_presentation` has an arm for — `dc+sd-jwt`, `mso_mdoc`, **and `ldp_vc`**, which is verified but deliberately not advertised by default, so the two lists are not interchangeable (conflating them rejected every JSON-LD verifier, including the e2e ones). `ldp_vc` carries an empty payload there and so is claimed wholesale: JSON-LD verification dispatches through `ssi`'s `AnySuite` on the proof inside the credential, so there is no fixed `proof_type` list an advertisement could be checked against. `jwt_vc_json` / `jwt_vp_json` genuinely are unsupported — `verify_presentation` has no `Presentation::JwtVp` arm. |
| `protocol_error.rs` | `ProtocolError`, `ErrorType` (re-exported from `openid4vp::core::error`) — standard-defined error responses for the presentation flow. |
| `internal_error.rs` | `InternalError` — non-protocol unexpected errors (authorization response parsing, JWE, KMS, VC verification, nonce generation, DCQL, Presentation Exchange, HTTP, ID token, `x509_san_dns` scheme (`X509`), etc.). |
| `tests.rs` | Integration-level unit tests for holder and verifier flows (`#[cfg(test)]`). |

## Key types / traits
- `Holder` — async trait: `get_authorization_request`, `present_credentials_auto`, `find_vcs_for_presentation`, `present_credentials`, `decline_authorization_request`, `get_credential_status`. With `delegate-sd-jwt` on, `present_credentials(_auto)` transparently produce a dSD-JWT (no holder binding) for any credential whose presentation input is targeted by a `delegate` transaction-data item — there is no separate `grant_delegation` method; the decision lives per-credential in `create_presentation_by_input`. A `delegate` item may only target dc+sd-jwt credentials; this is validated up front in `validate_transaction_data` (run while resolving the request in `get_authorization_request`), with the core `create_delegated_credential` format check as the safety net.
- `Verifier` — async trait: `create_authorization_request`, `verify_presentation`, and `verify_and_extract_presentation` (verifies like `verify_presentation` but also returns the raw presentations per credential id, so a Delegate Holder can store a returned dSD-JWT grant). A dSD-JWT grant is Holder-signed (proof of possession) and carries the request `aud`/`nonce` in its delegate payload, so it verifies through the normal path — there is no delegate-specific verify method.
- `HolderBuilder` / `VerifierBuilder` — async `build()` returns `impl Holder` / `impl Verifier`.
- `ResolvedAuthRequest` — complete parsed authorization request: client ID, metadata, presentation query, nonce, response type/mode, transaction data.
- `PresentationSession` — state kept by the verifier between request creation and response verification (nonce, resolved query, optional auth-request JWT).
- `PresentationResult` — `AuthorizationResponse(AuthorizationResponse)` | `RedirectUri(Url)` | `Presented`.
- `AuthorizationResponse` — `Plain(AuthorizationResponseObject)` | `Jwe(String)`.
- `JweDecrypt` — optional trait implemented by KMS to enable JWE-encrypted response modes.
- `ProtocolError` / `InternalError` — two-tier error split following 4xx/5xx convention.

## Constraints
- Trait objects use `#[cfg_attr(target_arch = "wasm32", async_trait(?Send))]` for WASM compatibility.
- `jwe.rs` and `jwe_utils.rs` depend on `one_core_asdk::one_crypto::jwe` for JWE construction and decryption.
- `JweDecrypt` is an optional capability: it must be implemented by the KMS only when encrypted response modes are needed; `VerifierBuilder` requires `KMS: Kms<KH> + JweDecrypt<KH>`.
- X.509 request generation is native-only: the upstream `X509Client` needs an `Arc<dyn Signer + Send + Sync>`, so the `Verifier` impl / builder carry a `KH: 'static` bound (a bound on an existing generic — no lifetime parameter was added to any type). `x509-cert` is a non-wasm dependency, so `Certificate` and everything in `x509.rs` bar the two type aliases are `#[cfg(not(wasm32))]`, and wasm returns an `X509` error for an `x509_*` `client_id`. **The chain API deliberately is not gated**: `VerifierMetadata.x5c_chain` and both `with_x509_certificate_chain` setters hold PEM bytes and compile everywhere, so the Verifier's shape does not fork per target — only the parsing and request-building do. Neither the wasm nor the uniffi wrapper exposes an OID4VP Verifier at all (holder only), so this feature reaches consumers through Node.js alone. `mod.rs` re-exports **no** x509 name for wasm, `X509Variant` included: wasm exposes no Verifier, so a wasm consumer has nothing to do with one. `X509Variant` stays crate-reachable as `x509::X509Variant` because the verifier's wasm stub and the ungated `X509SanDns` / `X509Hash` match arms in `build_authorization_request` still name it. Keep the `#[cfg]` split narrow: a re-export or import left ungated but used only on the native path warns on the wasm build (`wasm-pack build` in `wrappers/wasm` is what catches it — the native `cargo` commands never compile those branches). It is generation-only — the holder cannot consume such requests.
- The upstream request builder rejects any `client_id` prefix the Wallet Metadata does not advertise (`is_client_id_prefix_supported`), and cross-device OID4VP has no Wallet Metadata, so `default_wallet_metadata()` must keep advertising `x509_san_dns` / `x509_hash` for an X.509 `client_id` to work at all.
- Verifying an `mso_mdoc` VP needs issuer trust anchors from `VerifierBuilder::add_trusted_root_certificate`; the default metadata advertises the format regardless.
