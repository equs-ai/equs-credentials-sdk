# status_formats — Context

## Purpose
Provides the abstract `API` trait and concrete implementations for token-based VC revocation status lists, supporting Token Status List (draft-ietf-oauth-status-list) tokens in JWT form (issue and check) and CWT form (check only, native builds), and ISO/IEC 18013-5 Identifier Lists (check only, native builds).

## Files

| File | Role |
|------|------|
| mod.rs | `API` trait (create status list, get VC status), `StatusListFormat` enum, shared `Error` type. |
| status_list_token_jwt.rs | `StatusListJwt` — creates compressed bit-string status-list JWTs, fetches and decodes them to return `VCStatus`. Decodes `lst` with or without base64url padding, not through `JsonStatusList::decode`, which requires it. Accepts a plain JWT or this SDK's SD-JWT without disclosures; requires `typ: statuslist+jwt`; verifies the signature and its signer in `verify_status_list_signer` (via `SdJwtAPI::verify_vc_signer`), trusting `x5c` chains only for `get_vc_status_with_trusted_certs`. A token whose key is resolved through a DID (a DID URL `kid`, or a `kid`/`iss` DID) must be signed by the referenced credential's issuer DID, so it is rejected for a credential without one (an `x5c`-issued SD-JWT VC, every mdoc); a token signed by an `x5c` chain is checked against the trusted anchors instead. `get_status_list_entry(uri, idx, issuer, ..)` is the lookup itself, shared by the SD-JWT VC `status` claim and the mdoc MSO `status`. It asks for `application/statuslist+jwt, application/statuslist+cwt` (JWT only on wasm), hands a response typed `application/statuslist+cwt` to `StatusListCwt` and reads anything else as a JWT. The per-call cache keeps a JWT as is and a CWT base64url-encoded behind a `cwt:` prefix, and re-verifies a cached token on every lookup. On wasm a CWT still fails as "status list format not supported". |
| cwt.rs | `cwt::verify` (native only) — the checks shared by both CWT lists, for a `CwtProfile` (name for errors, media type, optional CoAP ID): a COSE_Sign1, tagged 18 or not, with nothing after it (the media type names one CWT, a single CBOR data item, RFC 8392; trailing bytes would make it a CBOR sequence, RFC 8742); protected `typ` (16) the profile's media type or its CoAP ID; protected `alg` ES256 over a P-256 certificate key or EdDSA over an Ed25519 one, the only pairs one-core verifies (it picks the algorithm from the key, so a mismatched `alg` is rejected rather than ignored); a protected `crit` naming anything but `alg`, `typ` or `x5chain` rejects the token (RFC 9052 §3.1); key only from `x5chain` (33, protected or unprotected), validated by `Truststore` against the caller's trusted certs under its `AnchorPolicy`, then the COSE signature verified with the leaf key; the signed claims must be one CBOR map with nothing after it; `sub` must equal the fetched URI, `iat` required and at most 60 seconds ahead, an `exp` in the past rejects it, a missing `exp` is accepted. No DID key resolution, so the JWT path's issuer-DID binding does not apply. `ttl` is not read. |
| status_list_token_cwt.rs | `StatusListCwt` (native only) — a CWT Status List Token (§5.2): `cwt::verify` with `application/statuslist+cwt` or CoAP ID 279, then `status_list` (65533) `bits`/`lst` decoded with `BitString::from_compressed_bytes`, as the JWT path does. |
| identifier_list_token_cwt.rs | `IdentifierListCwt` (native only) — an ISO/IEC 18013-5 2nd ed. Identifier List, the list an mdoc's MSO `status.identifier_list` names. `is_revoked` fetches it with `Accept: application/identifierlist+cwt`, requires a success status and that content type (lowercased prefix match, so parameters pass), and caps the body at 10 MiB, then calls `is_listed`. The status list fetch requires none of the three. Fetch failures are `Error::StatusListFetching`; `is_listed` runs `cwt::verify` with `typ` `application/identifierlist+cwt` (no CoAP ID is registered), rejects a token with a `status_list` claim (65533), requires claim 65530 to be `{"identifiers": {bstr: ...}}` with at most a million entries (checked after decoding, so the 10 MiB body cap is what bounds memory), ignores the values, and says whether the credential's id is a key, meaning revoked. The id is skipped in tracing and never put in an error. |

## Key types / traits
- `API<CS, ST, SL, MD>` — generic async trait for status list creation and VC status retrieval. `get_vc_status` trusts no X.509 anchors and takes the issuer DID from the credential claims' `iss`; `StatusListJwt::get_vc_status_with_trusted_certs` takes the issuer DID from its caller, plus trusted anchors and the `AnchorPolicy` their chain is checked under (used by `core::VerifierService`, which reads the issuer from the issuer-signed JWT and passes none for an mdoc).
- `StatusListFormat` — `StatusListTokenJwt(SLMetadata)` or `StatusListTokenCwt`.
- `CwtProfile` (native only) — what `cwt::verify` checks a CWT list against: a name for errors, the media type and an optional CoAP ID.
- `IdentifierListCwt` (native only) — `is_revoked` (fetch, then check) and `is_listed` (check a fetched token); both take the credential's id as bytes and return whether it is listed.
- `VCStatus` — `Valid | Invalid | Suspended | AppSpecific(u8)`.
- `VCStatuses` — `HashMap<usize, u8>` status index map used when creating a status list.
- `SLMetadata` — metadata for status list JWT creation (URL, size, count).
